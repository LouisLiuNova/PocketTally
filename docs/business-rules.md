# PocketTally 业务规则

本文档定义 PocketTally 当前账本领域的业务规则，并集中登记尚未决策的业务问题。业务规则描述“系统应当如何工作”，具体实施任务和优先级仍由 [`TODO.md`](../TODO.md) 管理。

> [!IMPORTANT]
> 本文档区分“已生效”“已确认但未完全落地”和“待决策”。只有前两类属于已确认的产品语义；待决策内容不得作为开发默认值或验收依据。

### 1.3 当前产品与运行边界

**状态：已确认｜决定日期：2026-09-09**

- PocketTally 当前面向个人、单用户和本地 SQLite 使用场景。
- 只有 PocketTally 应用可以写入数据库；未来导入功能也必须调用同一业务服务。
- 手工 SQL 和第三方程序直接写数据库不属于受支持能力。
- v0.1.0 是首个已发布的 SQLite 数据库基线。当前没有版本化数据库迁移；后续 Schema 变更前必须建立迁移，或明确版本兼容、升级前备份和恢复策略。
- v0.1.0 没有登录鉴权，只允许个人单用户在本地或可信内网使用；不得开放公网入口。v0.2 的单用户公网身份验证由 Issue #22 单独定义。
- 多用户、分布式写入、外部数据库写入和高并发控制不得作为当前设计的默认前提。

### 1.4 完整性职责

**状态：已确认但待完全落地**

| 层次 | 当前职责 |
| --- | --- |
| HTTP / Pydantic | 校验类型、格式、必填性和可以仅依据请求体判断的字段组合，并返回稳定错误。 |
| 业务服务 | 执行交易完整状态、分类、退款、余额和关系等跨字段、跨记录规则；创建、PATCH 和未来导入共用同一入口。 |
| SQLite | 保留主键、外键、唯一性、非空、封闭枚举、正金额及适合单行表达的 `CHECK`。 |

SQLite 不再承担分类用途、关系循环、退款累计等跨表业务规则，也不承诺直接 SQL 写入后的业务状态合法。应用启动时仍必须为每个连接启用外键约束。

当前公开 API 将请求格式校验失败映射为 `422 Unprocessable Entity`，资源不存在映射为 `404 Not Found`，名称、引用或业务状态冲突映射为 `409 Conflict`。错误体统一为 `{code, message, details?}`；不得向客户端返回 SQLite 或 SQLAlchemy 原始异常文本。

## 2. 产品与金额口径

### BR-MON-001：币种与金额精度

**状态：已生效**

- 当前系统只处理人民币 CNY，不在账户、交易或 HTTP 契约中保存币种字段。
- HTTP 金额以十进制元表达；服务端收到金额后立即转换为 `Decimal`。
- 金额统一使用 `ROUND_HALF_UP` 舍入到分，并以整数分 `amount_minor` 持久化和计算。
- 交易金额按舍入后的结果判断，必须严格大于 0。
- `NaN`、正负无穷和其他非有限数值不是合法金额。

### BR-MON-002：金额方向

**状态：已生效**

- 交易金额始终保存为正数。
- 资金增加或减少由交易类型、来源账户、目标账户和余额调整方向共同表达，不使用负交易金额表达支出或退款。

## 3. 账户规则

### BR-ACC-001：账户类型

**状态：已生效**

- 账户类型为封闭集合：`debit`、`credit`。
- `debit` 表示借记账户，余额不得小于 0。
- `credit` 表示信用账户，允许出现负余额。

### BR-ACC-002：账户创建与余额权威来源

**状态：已生效**

- 新建账户余额固定为 0，不提供初始余额字段。
- 账户余额是所有有效交易计算得到的可重建投影，不是可独立修改的账务事实。
- 账户创建和账户 PATCH 均不得接受余额字段。
- 没有有效交易的账户余额为 0。

### BR-ACC-003：余额调整

**状态：已生效**

- 人工调账必须创建 `balance_adjustment` 交易，不能直接改写账户余额。
- 余额调整只影响一个账户，使用 `increase` 或 `decrease` 明确资金方向。
- 余额调整不得指定目标账户和分类。
- 余额调整与普通交易一样保留发生时间和审计记录，也可以被作废。

### BR-ACC-004：名称唯一性

**状态：已生效**

- 账户名称在当前数据域内全局唯一。
- 唯一性按 SQLite `NOCASE` 规则比较，即 ASCII 大小写不敏感。

## 4. 交易规则

### BR-TXN-001：交易类型

**状态：已生效**

交易类型为封闭集合：

| 类型 | 含义 |
| --- | --- |
| `income` | 外部资金进入一个账户。 |
| `expense` | 资金从一个账户流出。 |
| `expense_refund` | 原支出的资金退回来源账户，并抵减支出。 |
| `transfer` | 资金在两个账户之间转移。 |
| `balance_adjustment` | 对一个账户执行有审计记录的余额调整。 |

当前代码与契约已实现以上交易类型。`expense_refund` 只能由专用退款入口创建，
不得用普通 `income` 交易代替。

### BR-TXN-002：账户路由

**状态：已生效**

| 交易类型 | 来源账户 | 目标账户 | 余额影响 |
| --- | --- | --- | --- |
| `income` | 必须为空 | 必填 | 目标账户增加交易金额。 |
| `expense` | 必填 | 必须为空 | 来源账户减少交易金额。 |
| `expense_refund` | 从原支出复制 | 必须为空 | 原支出来源账户增加退款金额。 |
| `transfer` | 必填 | 必填，且与来源账户不同 | 来源账户减少、目标账户增加相同金额。 |
| `balance_adjustment` | 必填，表示受影响账户 | 必须为空 | 按 `increase` 或 `decrease` 增减余额。 |

- 交易引用的账户必须存在。
- 转账对所有账户余额合计的净影响为 0。
- 路由校验应基于交易完整状态执行；PATCH 必须先合并原记录和请求字段，再校验结果。

创建、PATCH 和账本服务共用完整交易状态校验。SQLite 同时以单行 `CHECK`
保护五类账户路由和分类组合；未来导入入口仍必须调用相同服务。

### BR-TXN-003：原子记账

**状态：已生效**

- 交易写入、受影响账户余额重算和失败回滚必须位于同一个数据库事务中。
- 账本服务不在内部提前提交事务，事务的提交或回滚由调用方控制。
- 任一步骤失败时，不得留下交易已写入但余额未同步的中间状态。
- `accounts.amount_minor` 是服务层维护的可重建投影；SQLite 不使用跨表余额触发器。应用写入必须通过账本服务，并在同一事务中同步交易与余额投影。

### BR-TXN-004：有效交易与作废

**状态：已生效**

- `is_void = false` 且 `voided_at` 为空的交易为有效交易，参与余额计算；
  两个字段由数据库单行约束保持一致。
- 作废交易保留原记录、关系和作废时间，但不再参与余额计算，也不能 PATCH。
- `POST /transactions/{transactionId}/void` 是幂等业务操作。首次请求写入作废状态并
  撤销一次余额影响；重复请求返回首次结果，不刷新时间或再次重算余额。
- `GET /transactions` 返回分页对象 `{items,total,page,pageSize}`，默认隐藏作废交易；通过 `status=active|voided|all` 查询状态集合，旧的 `includeVoided` 参数不再属于契约；详情始终可读。
- 创建和 PATCH 不接受客户端提交 `isVoid` 或 `voidedAt`。

### BR-TXN-005：时间字段

**状态：已生效**

- `occurred_at` 表示交易实际发生时间，由客户端在创建交易时提供。
- `created_at` 表示服务器录入时间，由服务器生成。
- `updated_at` 表示记录或标签关系最近更新时间，由服务器维护。
- `voided_at` 表示交易作废时间；为空表示尚未作废。
- “入账时间”和完整交易状态尚未定义，不能用 `created_at` 或 `updated_at` 替代。
- HTTP 写入和交易查询时间必须带 `Z` 或 UTC 偏移；写入前转换为 UTC，SQLite 以 UTC 保存，响应带 `Z`。统计日期范围按 `Asia/Shanghai` 的左闭右开自然日边界计算。

### BR-TXN-006：交易修订

**状态：部分落地**

- 当前账本服务允许修改未作废交易，并在同一事务中重算余额。
- 修改后的交易仍必须满足金额、类型和账户路由规则。
- 是否允许已入账交易原地修改账务字段尚未决策；当前行为不代表长期产品规则。

## 5. 分类与标签

### BR-CAT-001：分类结构

**状态：已生效**

- MVP 保留树状分类。分类可以是顶级分类，也可以通过 `parent_category_id` 指向一个父分类。
- 分类名称在当前数据域内全局唯一，并按 SQLite `NOCASE` 规则比较。
- 分类的必填 `purpose` 只允许 `income` 和 `expense`，不提供 `both`；普通收入和支出必须分别引用对应用途的分类，转账和余额调整不得引用分类。
- 父分类和子分类的用途必须相同，包括仅用于聚合的父分类；用途在分类创建后不可修改。
- 创建和移动分类时通过统一分类服务拒绝自身引用、多节点循环和不存在的父分类。
- 分类完整性校验沿候选祖先链有限迭代；即使已有异常环也会返回稳定业务错误，不会无限递归。
- 分类允许更新名称、描述、图标和颜色。修改名称会改变历史记录和报表中的展示名称，但不会改变交易引用或账务用途。
- 分类允许移动。含子分类节点移动的用户确认和风险提示由前端负责，后端不接收确认字段。后端只更新根节点的 `parent_category_id`，并在同一事务中校验目标父分类、循环、父子用途和现有子树内部用途，失败时整体回滚。
- SQLite 保留自引用外键，但不使用递归触发器保护跨行树结构；PocketTally 的分类写入必须通过分类服务。
- 父分类被子分类引用时不能物理删除。分类树最大深度当前不设产品限制，但实现必须使用可终止的遍历并防御已有异常关系。

### BR-TAG-001：交易标签

**状态：已生效**

- 标签是可由多笔交易复用的独立实体。
- 一笔交易不能重复关联同一标签。
- 标签名称在当前数据域内全局唯一，并按 SQLite `NOCASE` 规则比较。
- 增删交易标签关联应更新交易的 `updated_at`。

### BR-RES-001：基础资源删除

**状态：已生效**

- 账户、分类和标签只有在未被交易、子分类或关联记录引用时才允许物理删除。
- 被引用资源的删除请求返回稳定的 `409 Conflict`，不得级联删除交易，也不得为了删除资源而静默清空历史关系。
- 成功删除返回 `204 No Content`，且不返回响应体。
- 归档与物理删除是不同能力；未来需要隐藏已停用资源时，应单独设计 `archived_at` 或等价状态。

## 6. 退款与报表规则

### BR-REF-001：支出退款

**状态：已生效｜决定日期：2026-09-03｜实现日期：2026-09-07**

- 支出退款使用独立的 `expense_refund` 交易类型，不复用普通 `income` 类型。
- 退款必须关联一笔有效的原交易。
- 退款不得关联自身，退款关系不得形成循环。
- 一笔原交易可以有一笔或多笔退款；所有有效退款累计金额不得超过原交易金额。
- 退款必须沿原交易资金路径反向退回，不允许由客户端选择其他账户。
- 已作废或已被冲正的退款不计入有效退款累计金额。
- 支出退款在报表中冲减原支出，不记为普通收入，并沿用原支出分类。
- 客户端只提交 `refundOfTransactionId`、金额、发生时间和可选说明；退款账户和分类由服务端从原支出复制，客户端不能覆盖。
- `expense_refund` 不通过普通交易创建或 PATCH 接口伪造，只能经过退款业务入口创建。
- 原支出存在有效退款时，只允许维护说明、发生时间和标签；修改类型、金额、账户、
  分类或作废原支出前，必须先作废全部有效退款。

### BR-RPT-001：转账报表口径

**状态：已生效**

- 转账只改变账户之间的资金分布，不构成收入或支出。
- 转账不得进入收入、支出或对应分类的统计。
- 最小收支统计分别给出收入、原始支出、有效退款和净支出；转账与余额调整排除，
  已作废交易不参与统计。

### BR-RPT-002：期间统计与下钻口径

**状态：已生效｜关联 Issue：#15**

- 统计日期范围使用上海本地日期的左闭右开边界，响应回传 `timezone: "Asia/Shanghai"`；日、周、月时间桶首尾裁剪且无数据桶补零。
- 消费净支出、分类和 Tag 先按原支出发生时间筛选，再扣除该原支出的全部有效退款；退款发生日期不改变原支出所属期间。
- 现金流和日历按每笔交易自身发生时间统计收入、支出和退款，实际净现金流为收入加退款减支出；退款不计入普通收入。
- 分类按当前分类树递归归集，Tag 是非互斥维度；同一支出关联多个 Tag 时，每个 Tag 计入完整净额，不提供 Tag 总计或占比。
- 统计金额和消费下钻金额使用整数分字段；交易 CRUD 的金额仍使用人民币元 JSON number。

### BR-RPT-003：大账本统计查询边界

**状态：已生效｜关联 Issue：#16**

- 退款抵减和 Tag 统计必须在数据库侧通过有界筛选、关联与聚合完成，不得把期间内全部
  交易 ID 展开为 `IN (...)` 参数，也不得下载全部交易到浏览器聚合。
- 十万笔正确性回归属于默认后端测试；机器相关的性能门禁独立执行，每个接口预热后
  测量 20 次完整请求，按 nearest-rank 计算的 p95 必须不超过 1 秒。
- 性能验收必须使用独立临时账本，包含有效退款和作废退款，并记录运行环境、数据构成、
  测量方法与逐接口结果。

## 7. 待决策业务规则

本节是业务决策登记表。每项决策完成后，应记录结论和日期，将确定的规则移入前述章节，并更新 `TODO.md` 的实施状态。

### DEC-CAT-001：分类用途与父子一致性

**状态：已决定｜决定日期：2026-09-07｜关联 Issue：#5**

分类严格使用必填的 `income`、`expense` 封闭用途集合，不提供通用用途。父子分类用途必须一致，分类用途创建后不可修改，因此已引用分类不会因用途更新而使历史交易失配。普通收入和支出必须选择用途匹配的分类；转账和余额调整不使用分类。分类移动遵循 `BR-CAT-001` 的前端确认和后端事务校验职责边界。

### DEC-REF-001：退款支持范围

**状态：已决定｜决定日期：2026-09-03｜关联 TODO：P2 退款与报表**

当前 MVP 只支持支出退款。收入退款、转账退款和冲正均不进入本次范围；出现明确产品场景后重新建项。

### DEC-REF-002：退款与冲正关系模型

**状态：已决定｜决定日期：2026-09-03｜关联 TODO：P2 退款与报表**

废弃 `is_refund` 与通用的 `related_transaction_id`。支出退款使用独立的
`expense_refund` 类型和 `refund_of_transaction_id`；冲正不进入当前 MVP，因此暂不增加
`reversal_of_transaction_id`。当前没有已发布数据库，不保留旧字段兼容层。

### DEC-REV-001：冲正定义

**状态：待决策｜关联 TODO：P1 核心账本规则**

需要决定：

1. 冲正是否必须完整抵消原交易且金额相等；
2. 每笔原交易是否最多存在一笔有效冲正；
3. 原交易已有部分退款时，允许冲正、拒绝冲正还是先处理退款；
4. 冲正交易能否再次成为退款或冲正的目标；
5. 冲正、作废和删除之间的产品边界。

### DEC-LIF-001：交易生命周期与入账语义

**状态：延后评估｜关联 TODO：延后评估**

当前个人 MVP 保留现有“有效 / 已作废”语义，不默认引入企业会计式完整入账状态。出现导入待确认、账单结算或不可变凭证需求时，再定义交易状态以及发生、录入、入账、修改、作废和冲正时间的关系。届时至少应明确：

- 哪些状态属于有效交易并影响余额；
- 每个状态允许修改的字段；
- 已入账交易是否禁止原地修改金额、类型、账户、分类和发生时间；
- 是否统一通过“冲正原交易并创建更正交易”修复账务错误；
- 描述、标签等非账务字段在入账后是否仍可修改。

### DEC-RPT-001：拆分交易与报表归属

**状态：待决策｜关联 TODO：P2 退款与报表**

当前 MVP 已按 `BR-RPT-002/003` 确定并实现上海时区期间、退款双重归属、分类树递归
归集、Tag 非互斥维度、整数分下钻和数据库侧有界聚合。以下能力仍延后决定：

1. 一笔交易能否拆分到多个分类；
2. 拆分金额之和与交易总额的精度和相等约束；
3. 冲正和更正交易在期间报表中的归属日期与抵减方式；
4. 拆分交易与退款、作废、冲正和更正之间的组合规则。

### DEC-AUTH-001：单用户公网鉴权与多用户隔离

**状态：MVP 后续｜关联 TODO：v0.2 公网单用户发布、延后评估**

- v0.2 单用户公网发布：Issue #22 负责威胁模型、单用户身份验证、会话和公网安全边界。
  该范围不引入多用户所有权或资源隔离；验收完成前不得把 v0.1.0 部署到公网。
- 更远期多用户能力：出现明确需求后，再定义账户、交易、分类和标签的所有者，以及跨用户
  引用、名称唯一性作用域和数据迁移规则。不得把这些规则当作单用户鉴权的前置设计。
