# PocketTally 业务规则

本文档定义 PocketTally 当前账本领域的业务规则，并集中登记尚未决策的业务问题。业务规则描述“系统应当如何工作”，具体实施任务和优先级仍由 [`TODO.md`](../TODO.md) 管理。

> [!IMPORTANT]
> 本文档区分“已生效”“已确认但未完全落地”和“待决策”。只有前两类属于已确认的产品语义；待决策内容不得作为开发默认值或验收依据。

## 1. 文档约定

### 1.1 规则状态

| 状态 | 含义 |
| --- | --- |
| 已生效 | 业务含义已确认，且当前主要实现层已经执行该规则。 |
| 部分落地 | 业务含义已确认，但 HTTP 契约、服务、ORM、DDL、导入或测试之间仍存在缺口。 |
| 待决策 | 尚未形成产品决策，不属于当前规范。 |
| MVP 后续 | 已识别但明确不进入当前 MVP。 |

### 1.2 事实来源与优先级

发生描述冲突时，按以下顺序处理：

1. 本文档中的已确认业务规则；
2. `TODO.md` 中尚未完成的实施范围和验收要求；
3. 当前 HTTP Schema、账本服务、ORM、SQLite DDL 与自动化测试；
4. `TODO-IMP.md` 中的历史讨论和推荐方案。

`TODO-IMP.md` 不具有规范性，其中与本文档不一致的内容均视为历史背景。

## 2. 产品与金额口径

### BR-MON-001：币种与金额精度

**状态：已生效**

- 当前系统只处理人民币 CNY，不在账户、交易或 HTTP 契约中保存币种字段。
- HTTP 金额以十进制元表达；服务端收到金额后立即转换为 `Decimal`。
- 金额统一使用 `ROUND_HALF_UP` 舍入到分，并以整数分 `amount_minor` 持久化和计算。
- 交易金额按舍入后的结果判断，必须严格大于 0。
- `NaN`、正负无穷和其他非有限数值不是合法金额。

### BR-MON-002：金额方向

**状态：已生效**

- 交易金额始终保存为正数。
- 资金增加或减少由交易类型、来源账户、目标账户和余额调整方向共同表达，不使用负交易金额表达支出或退款。

## 3. 账户规则

### BR-ACC-001：账户类型

**状态：已生效**

- 账户类型为封闭集合：`debit`、`credit`。
- `debit` 表示借记账户，余额不得小于 0。
- `credit` 表示信用账户，允许出现负余额。

### BR-ACC-002：账户创建与余额权威来源

**状态：已生效**

- 新建账户余额固定为 0，不提供初始余额字段。
- 账户余额是所有有效交易计算得到的可重建投影，不是可独立修改的账务事实。
- 账户创建和账户 PATCH 均不得接受余额字段。
- 没有有效交易的账户余额为 0。

### BR-ACC-003：余额调整

**状态：已生效**

- 人工调账必须创建 `balance_adjustment` 交易，不能直接改写账户余额。
- 余额调整只影响一个账户，使用 `increase` 或 `decrease` 明确资金方向。
- 余额调整不得指定目标账户和分类。
- 余额调整与普通交易一样保留发生时间和审计记录，也可以被作废。

### BR-ACC-004：名称唯一性

**状态：已生效**

- 账户名称在当前数据域内全局唯一。
- 唯一性按 SQLite `NOCASE` 规则比较，即 ASCII 大小写不敏感。

## 4. 交易规则

### BR-TXN-001：交易类型

**状态：已生效**

交易类型为封闭集合：

| 类型 | 含义 |
| --- | --- |
| `income` | 外部资金进入一个账户。 |
| `expense` | 资金从一个账户流出。 |
| `transfer` | 资金在两个账户之间转移。 |
| `balance_adjustment` | 对一个账户执行有审计记录的余额调整。 |

### BR-TXN-002：账户路由

**状态：部分落地**

| 交易类型 | 来源账户 | 目标账户 | 余额影响 |
| --- | --- | --- | --- |
| `income` | 必须为空 | 必填 | 目标账户增加交易金额。 |
| `expense` | 必填 | 必须为空 | 来源账户减少交易金额。 |
| `transfer` | 必填 | 必填，且与来源账户不同 | 来源账户减少、目标账户增加相同金额。 |
| `balance_adjustment` | 必填，表示受影响账户 | 必须为空 | 按 `increase` 或 `decrease` 增减余额。 |

- 交易引用的账户必须存在。
- 转账对所有账户余额合计的净影响为 0。
- 路由校验应基于交易完整状态执行；PATCH 必须先合并原记录和请求字段，再校验结果。

> [!WARNING]
> 当前账本服务已执行账户路由校验，但创建/PATCH Schema、ORM 和 SQLite DDL 尚未统一执行全部组合约束，导入路径也尚未建立。完成标准见 `TODO.md` 的“统一交易路由和分类约束”。

### BR-TXN-003：原子记账

**状态：已生效**

- 交易写入、受影响账户余额重算和失败回滚必须位于同一个数据库事务中。
- 账本服务不在内部提前提交事务，事务的提交或回滚由调用方控制。
- 任一步骤失败时，不得留下交易已写入但余额未同步的中间状态。

### BR-TXN-004：有效交易与作废

**状态：部分落地**

- `voided_at` 为空的交易为有效交易，参与余额计算。
- 作废交易保留原记录和作废时间，但不再参与余额计算。
- 已作废交易不能通过账本服务直接修改，也不能重复作废。
- 当前只定义了作废对余额的影响；谁可以作废、允许作废的状态和时间限制仍待生命周期决策。

### BR-TXN-005：时间字段

**状态：部分落地**

- `occurred_at` 表示交易实际发生时间，由客户端在创建交易时提供。
- `created_at` 表示服务器录入时间，由服务器生成。
- `updated_at` 表示记录或标签关系最近更新时间，由服务器维护。
- `voided_at` 表示交易作废时间；为空表示尚未作废。
- “入账时间”和完整交易状态尚未定义，不能用 `created_at` 或 `updated_at` 替代。

### BR-TXN-006：交易修订

**状态：部分落地**

- 当前账本服务允许修改未作废交易，并在同一事务中重算余额。
- 修改后的交易仍必须满足金额、类型和账户路由规则。
- 是否允许已入账交易原地修改账务字段尚未决策；当前行为不代表长期产品规则。

## 5. 分类与标签

### BR-CAT-001：分类结构

**状态：部分落地**

- 分类可以是顶级分类，也可以通过 `parent_category_id` 指向一个父分类。
- 分类名称在当前数据域内全局唯一，并按 SQLite `NOCASE` 规则比较。
- 当前没有分类用途字段，也没有形成收入/支出用途和父子用途一致性规则。
- 当前没有完整定义分类循环、父分类删除和分类树最大深度等约束。

### BR-TAG-001：交易标签

**状态：已生效**

- 标签是可由多笔交易复用的独立实体。
- 一笔交易不能重复关联同一标签。
- 标签名称在当前数据域内全局唯一，并按 SQLite `NOCASE` 规则比较。
- 增删交易标签关联应更新交易的 `updated_at`。

## 6. 已确认但尚未实现完整的业务规则

以下规则已经形成业务方向，但仍需要设计和实现，不应标记为已生效。

### BR-REF-001：退款基本约束

**状态：部分落地**

- 退款必须关联一笔有效的原交易。
- 退款不得关联自身，退款关系不得形成循环。
- 一笔原交易可以有一笔或多笔退款；所有有效退款累计金额不得超过原交易金额。
- 退款必须沿原交易资金路径反向退回，不允许由客户端选择其他账户。
- 已作废或已被冲正的退款不计入有效退款累计金额。
- 支出退款在报表中冲减原支出，不记为普通收入，并沿用原支出分类。

> [!WARNING]
> 当前 `is_refund` 与 `related_transaction_id` 仅提供数据字段，尚未执行上述关系、累计金额、并发和报表规则。收入退款范围、关系字段模型及退款与冲正的边界仍待决策。

### BR-RPT-001：转账报表口径

**状态：部分落地**

- 转账只改变账户之间的资金分布，不构成收入或支出。
- 转账不得进入收入、支出或对应分类的统计。
- 当前尚未建立完整报表实现和回归测试。

## 7. 待决策业务规则

本节是业务决策登记表。每项决策完成后，应记录结论和日期，将确定的规则移入前述章节，并更新 `TODO.md` 的实施状态。

### DEC-CAT-001：分类用途与父子一致性

**状态：待决策｜关联 TODO：P1 核心账本规则**

需要决定：

1. 分类是否严格分为 `income` 和 `expense`；
2. 是否允许同时用于收入和支出的通用分类；
3. 父分类和子分类是否必须具有相同用途；
4. 修改分类用途时，如何处理已经引用该分类的交易。

决策至少应明确分类用途枚举、合法父子组合、历史数据处理方式和报表聚合口径。

### DEC-REF-001：退款支持范围

**状态：待决策｜关联 TODO：P1 核心账本规则**

需要决定普通退款支持以下哪一范围：

- 仅支出退款；
- 支出和收入退款；
- 转账是否只能使用冲正，不进入普通退款模型。

若支持收入退款，还必须定义其报表归属和对原收入分类的抵减方式。

### DEC-REF-002：退款与冲正关系模型

**状态：待决策｜关联 TODO：P1 核心账本规则**

需要决定是否废弃 `is_refund` 与通用的 `related_transaction_id`，改用语义明确的关系字段：

- `refund_of_transaction_id`：支持部分退款和多次退款；
- `reversal_of_transaction_id`：表示一次完整冲正。

决策还应明确一笔交易能否同时具有两种关系，以及关系字段的迁移和兼容策略。

### DEC-REV-001：冲正定义

**状态：待决策｜关联 TODO：P1 核心账本规则**

需要决定：

1. 冲正是否必须完整抵消原交易且金额相等；
2. 每笔原交易是否最多存在一笔有效冲正；
3. 原交易已有部分退款时，允许冲正、拒绝冲正还是先处理退款；
4. 冲正交易能否再次成为退款或冲正的目标；
5. 冲正、作废和删除之间的产品边界。

### DEC-LIF-001：交易生命周期与入账语义

**状态：待决策｜关联 TODO：P2 生命周期与报表**

需要定义交易状态，以及发生、录入、入账、修改、作废和冲正时间的关系。至少应明确：

- 哪些状态属于有效交易并影响余额；
- 每个状态允许修改的字段；
- 已入账交易是否禁止原地修改金额、类型、账户、分类和发生时间；
- 是否统一通过“冲正原交易并创建更正交易”修复账务错误；
- 描述、标签等非账务字段在入账后是否仍可修改。

### DEC-RPT-001：拆分交易与报表归属

**状态：待决策｜关联 TODO：P2 生命周期与报表**

需要决定：

1. 一笔交易能否拆分到多个分类；
2. 拆分金额之和与交易总额的精度和相等约束；
3. 分类树按本级、子树或两者分别聚合；
4. 退款、冲正、作废和更正交易在期间报表中的归属日期与抵减方式。

### DEC-AUTH-001：用户、所有权与数据隔离

**状态：MVP 后续｜关联 TODO：MVP 后续功能**

引入多用户能力前，需要定义账户、交易、分类和标签的所有者，以及跨用户引用、名称唯一性作用域和数据迁移规则。当前 MVP 不据此实现鉴权或资源隔离。

## 9. 决策记录模板

新增或关闭业务决策时使用以下格式：

```markdown
### DEC-XXX-NNN：决策标题

**状态：待决策 / 已决定｜决定日期：YYYY-MM-DD｜负责人：姓名或角色**

背景：说明为什么需要该决策。

决策：写明唯一、可执行的业务结论。

影响：列出 HTTP 契约、服务、数据模型、迁移、报表和测试影响。

验收：列出可以独立验证的结果。
```
